## Contract and activation gates

The component reads `https://myaimarketing.worker-bee.app/api/weekly-subscriptions?availability=1` without credentials. It exposes a form only when the backend explicitly enables availability, returns `weekly-practice-v1`, `one_lesson_email_per_week_total`, the exact Language Threshold privacy URL, a Turnstile public site key/action/cData requirement, and at least one ready known track. Unknown, duplicated, malformed, unavailable, failed, or timed-out configuration fails closed. Backend deployment, allowed origins, Turnstile hostname/site-key configuration and server-side token verification remain backend-owned prerequisites. No static secret or site key is embedded here.

Known tracks are `junior-parent-orientation` (10 weeks), `homeschool-spanish` (50), and `language-threshold-module-lessons` (50). One choice is required, no choice is preselected, and individually unavailable tracks are disabled. The email field accepts only an adult address. No child identity, name, recording, progress, purchase, or download details are collected. The adult and optional weekly permission checkboxes start unchecked. Privacy links to https://languagethreshold.com/privacy.

POST uses only `{action:"request",email,trackId,adult:true,weeklyConsent:true,policyVersion:"weekly-practice-v1",turnstileToken,requestId,website}`. The request ID is a UUIDv4 and also the widget cData; a network retry retains that ID and obtains a fresh token. Editing email/track after an attempt creates a new request ID. A synchronous guard prevents duplicate simultaneous submissions. Email and token are never written to browser storage.

Only HTTP 202 with `status:"request_received"` displays a conditional confirmation invitation receipt. It does not claim enrollment, delivery, or active subscription. Unexpected 200, errors, timeouts, and 403/429/503 never show success. Weekly lessons must start only after the separate backend confirmation process. Backend must also enforce adult-only intake, consent version, single active weekly track/pacing, anti-abuse/budgets, suppression and unsubscribe, idempotency, and approved ready campaign/resource mappings; frontend checks do not replace those controls.

## Verification

`node --test tests/weekly-signup.test.mjs`: four contract cases passed. `npm run build`: passed. `scripts/check-weekly-signup-ui.mjs`: 17 isolated browser cases passed (availability fail-closed, missing verification, all three tracks, unchecked choices/permissions, four responsive widths, duplicate submission, retry identity/token behavior, changed identity, errors, and unavailable track). Results and screenshots are in `tests/reports/weekly-signup-ui.json` and `tests/reports/weekly-screenshots/`. Every external request in that test was intercepted: no real email or provider request was sent. Desktop and mobile screenshots were visually inspected; no horizontal overflow was found.

Run the browser check with `PLAYWRIGHT_MODULE` pointing to an installed Playwright ESM module and `CHROMIUM_EXECUTABLE_PATH` pointing to local Chrome. It binds only localhost, uses synthetic public configuration, and never reads app environment files.

Turnstile implementation follows Cloudflare's [widget configuration](https://developers.cloudflare.com/turnstile/get-started/client-side-rendering/widget-configurations/) and [client rendering](https://developers.cloudflare.com/turnstile/get-started/client-side-rendering/) documentation: explicit widget lifecycle, `cData`, action, flexible width, single-use token, expiry/error clearing, and reset after attempts. Live hostname/origin verification and a real opt-in confirmation have not been exercised in this isolated branch. No production deployment or live signup is included in this proof.
